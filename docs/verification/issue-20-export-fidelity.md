# 이슈 20 — 이미지 선명도 비교

2026-11-18 · [#20](https://github.com/yourjinKR/drop-your-code/issues/20) · [비교 계획](../plans/issue-20-export-fidelity.md)

Windows에서 Chrome 157, Node 22.23.2, 로컬 Vite를 사용했다. 구현 기준은 #19가 포함된 `main`의 `fdb5e2b`이다. 생성한 Java 예제 5줄에 기본 모노스페이스 14px, Dark syntax, 코드 패딩 24px, 외부 패딩 48px를 사용했다. 모든 출력은 논리 치수 531 × 295의 동일 모델을 사용했다.

## 해상도와 붙여넣기

| 출력 | 픽셀 치수 | 파일 바이트 |
|---|---:|---:|
| SVG | 531 × 295 논리 크기 | 3,059 |
| PNG 2× | 1,062 × 590 | 54,708 |
| PNG 4× | 2,124 × 1,180 | 139,411 |
| JPG 2× | 1,062 × 590 | 37,138 |
| WebP 2× | 1,062 × 590 | 12,620 |

- SVG를 1,062 × 590에서 바로 그린 결과와 2× PNG를 디코딩한 결과의 RGBA 픽셀이 모두 일치했다. 이 환경의 기본 SVG→Canvas 경로에서는 추가적인 픽셀 손실을 관찰하지 않았다.
- 현재 `Copy Image`로 복사한 2× PNG와 같은 복사 함수에 4× 인코딩을 연결한 실험을 각각 `Ctrl+V`로 로컬 편집 영역에 붙여넣었다. 두 경우 모두 원래 픽셀 치수와 RGBA 값을 유지했다. 붙여넣은 파일은 각각 48,635바이트와 120,664바이트였다.
- 코드 영역에서 한 채널이라도 차이가 16을 넘은 픽셀의 비율은 531 × 295 표시에서 2.98%, 1,062 × 590 표시에서 1.95%였다. 2×를 2,124 × 1,180으로 확대해 네이티브 4×와 비교하면 3.47%였고, 확대 비교에서 4×의 글자 윤곽이 더 또렷했다. 비율은 두 렌더링의 차이를 나타내며 선명도의 절대 점수로 쓰지 않는다. 축소와 확대에는 같은 Canvas 이미지 보간을 사용했다.
- 4× PNG는 2× 대비 픽셀 수가 4배였고, 이 예제의 파일 크기는 약 2.55배였다. 각 배율을 7회씩 번갈아 인코딩한 두 실행의 중앙값은 2× 10.5·20.8ms, 4× 25.2·42.9ms였다. 이 수치는 짧은 예제의 로컬 측정값이다.
- 투명 설정에서 SVG·4× PNG·2× WebP의 모서리와 코드 창 내부 alpha는 각각 0과 255였다. JPG는 배경을 채워 둘 다 255였다.

## 렌더링 경로, 글꼴, 압축

- 같은 글꼴과 모델 좌표로 코드 텍스트만 Canvas에 직접 그린 2× 실험에서, SVG 결과와 채널 차이가 16을 넘는 픽셀은 코드 영역의 0.09%였다. 글자 그리기 방식만 교체하는 작업의 효과는 이 예제에서 작았다. 이 실험의 비교 범위는 코드 영역이다.
- 화면 기본 글꼴 스택에서 가장 긴 줄의 폭은 384.86px였고, Courier New로 측정하면 420.07px였다. 독립 SVG가 다른 글꼴로 열리는 경우 글자 폭과 기존 토큰 좌표가 어긋날 수 있으므로, 운영체제 간 SVG 일치가 중요해지면 글꼴 정책을 먼저 검증한다.
- 2× PNG를 기준으로 코드 영역에서 채널 차이 16을 넘는 픽셀은 JPG 0.53%, WebP 0.77%였다. 같은 픽셀을 Canvas 품질 `0.95`로 인코딩하면 각각 0.29%, 0.21%였고 크기는 44,602바이트와 20,766바이트가 됐다. 품질을 높이면 이 예제에서 색과 경계 오차가 줄고 파일은 커졌다.

## 결정 제안

전용 SVG 렌더러와 래스터 다운로드 2× 기본값을 유지한다. `Copy Image`는 고화질 4× PNG로 제공한다. 비교 범위는 Windows Chrome과 로컬 붙여넣기이며, 고용량 코드 처리 확대는 보류한다.

## 검증 실행

로컬에서 `node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 4184 --strictPort`로 앱을 실행하고, 임시 Playwright 측정 스크립트에서 `buildSnapshotModel`, `renderSnapshotSvg`, `encodeSnapshot`, `copySnapshotPng`를 호출했다. `Copy Image`와 붙여넣기는 브라우저 조작으로 실행했다. 파일별 치수, 투명 배경 및 창의 alpha, SVG와 PNG의 픽셀 일치, 두 붙여넣기의 픽셀 일치를 검증했다.

## 초기 4× 복사 선택 구현 검증

Windows Chrome의 320px 화면에서 `Copy scale`의 기본 2×, 다운로드 형식이 SVG인 상태의 4× PNG 복사, 2× 복귀를 검증했다. 실제 클립보드 PNG는 1,664 × 844였고 바깥 alpha는 0, 코드 창 내부 alpha는 255였다. 추가한 브라우저 회귀 테스트는 구현 전 실패하고 구현 후 통과했다. [브라우저 테스트](../../tests/browser/png-clipboard.spec.ts)

## 레퍼런스의 글자 선명도 비교

첨부 PNG는 2,836 × 764였다. 비슷한 줄 길이의 합성 Java 예제로 Windows Chrome의 `Copy Image (4×)`를 눌러 전후 결과를 수집했다. 비교한 단어는 양쪽에 있는 `package`다. 글자 색과 배경 색의 차이를 기준으로 25% 이상 채워진 글자 픽셀을 잡고, 그중 글자 색과 완전히 일치하는 픽셀의 비율과 글자 높이를 계산했다. 값은 원본 크기의 해당 단어에서 측정했다.

| 이미지 | 원본 픽셀 치수 | `package` 글자 높이 | 글자 색과 일치하는 내부 픽셀 비율 |
|---|---:|---:|---:|
| 첨부 레퍼런스 | 2,836 × 764 | 53px | 60.6% |
| 기존 기본 글꼴, 4× 복사 | 2,864 × 1,180 | 51px | 56.6% |
| Cascadia 우선, 4× 복사 | 3,016 × 1,180 | 54px | 62.6% |

세 이미지를 Lanczos로 폭 1,200px에 맞추면 글자 높이는 각각 23px, 22px, 22px였다. 이 크기에서 95% 이상 채워진 글자 픽셀의 비율은 각각 39.5%, 42.7%, 40.6%였다. 원본의 글꼴 차이와 표시 크기에 따른 결과를 각각 확인했다.

기본 14px·4×에서 획을 더 뚜렷하게 보이도록 기본 시스템 글꼴에서 Cascadia Mono와 Cascadia Code를 우선한다. 브라우저에 설치된 글꼴을 사용하므로 플랫폼별 대체 글꼴은 달라질 수 있다. Java의 인터페이스명 및 메서드명 색 대비에는 레퍼런스와 차이가 있다. [구문 강조 #23](https://github.com/yourjinKR/drop-your-code/issues/23)

`npm run typecheck`와 `npm run test -- --maxWorkers 4`의 147개 테스트가 통과했다. 설치된 Windows Chrome의 프로덕션 빌드에서 미리보기·스타일·네 가지 다운로드·PNG 클립보드 브라우저 테스트 16개를 실행해 모두 통과했다.

## 도구 모음 Export 설정과 4× 복사 검증

상단 화살표로 형식과 JPG 배경을 선택했다. `Export`를 눌러 네 가지 파일을 다운로드하고, SVG 형식이 선택된 상태에서 `Copy Image`로 1,664 × 844의 투명 4× PNG를 복사했다. `Enter`, `Tab`, `Escape`, 바깥 클릭으로 열고 닫는 경로와 Escape 후 포커스 복귀를 확인했다. 320px 터치 화면에서 화살표는 44 × 44px였고 드롭다운과 문서가 화면 폭 안에 머물렀다.

`npm run typecheck`, `npm run test -- --maxWorkers 4`의 147개 테스트가 통과했다. 설치된 Windows Chrome의 프로덕션 빌드에서 `npm run test:browser`의 다운로드·클립보드·미리보기·편집기·기초 동작 테스트 25개가 통과했다.
